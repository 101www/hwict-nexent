先打开[真实graph.json](D:/JavaProject/huawei/nexent-cognitive-agent/data/processed/graph.json)，搜索`E-66e12bb6b24d32`。下面是该边的部分真实字段，其他字段省略：

`headId`是起点的ID，`tailId`是终点的ID，`relation`是关系名。它表达的是“这个方案，是这个人群的首选方案”。这两个ID必须在顶层`nodes`数组中找到对应节点。

比如人群节点有这些字段：

```json

  "name": "高血压合并糖尿病患者",
  "type": "Population"

```

这里也只展示部分字段。注意，前文为方便理解写“A方案”，但存储的方案节点全名其实是“血管紧张素转换酶抑制剂或血管紧张素II受体阻滞剂”，它的`type`是`DrugRegimen`。不是图里真有一个名叫“A方案”的节点。

一条边只要写了其他节点的ID，就形成连接。另一个边如果共享这个ID，程序就能接着查，这就是“沿路径找”的数据基础。画出来的箭头图只是这些记录的可视化。

`section`与`semantic_section`不同是已记录的排版归属疑点，不能把它们当成两个已核验的章节。`start/end`是`blocks`中对应原文块内的字符偏移，不是PDF坐标，也不是整份文件的偏移。

## 9. Java怎么“识别图谱”：解析约定字段，建立两个索引

`Files.readString(source)`拿到JSON文本；Jackson的`mapper.readTree(...)`把文本解析为`JsonNode`树。这个`readTree`里的树是JSON层级树，不表示它已经理解了医学图谱。

它能处理图谱，是因为代码知道约定的字段名。`graph.path("nodes")`取节点数组；`edge.path("headId").asText()`取边的起点字符串；`asText()`就是把该JSON值当成文字读取。

第33行起检查`meta`和必要数组；第41行把节点按ID登记到`nodes`这个Map里：

```java
index(graph.path("nodes"), nodes, "node");
index(graph.path("blocks"), blocks, "block");
```

`index()`第92行起遍历数组，把每条记录存成`ID → 记录`。空ID或重复ID会报错。于是之后`repo.node(id)`不必每次扫描整份数组。

**另一个重要索引叫邻接表**。它是`节点ID → 与该节点相连的边列表`，在第43行起构建：

```java
for (JsonNode edge : graph.path("edges")) {
    String head = edge.path("headId").asText(), tail = edge.path("tailId").asText();
    if (!nodes.containsKey(head) || !nodes.containsKey(tail)) {
        // 不删除异常断言，也不默默跳过。候选集合允许保留未解决端点。
        throw new IOException("关系端点不存在: " + edge.path("id").asText());
    }
    adjacency.computeIfAbsent(head, ignored -> new ArrayList<>()).add(edge);
    if (!head.equals(tail)) {
        adjacency.computeIfAbsent(tail, ignored -> new ArrayList<>()).add(edge);
    }
}
```

`computeIfAbsent`的含义是：如果这个ID尚无边列表，就先创建空列表；然后`add(edge)`把当前边登记进去。对同一条边，起点和终点各登记一次，方便正向和反向查找；不会因此把原边的医学关系反转。

只看本例三条边时，邻接表可以缩写成下面这样。P、R、D1、D2是此处教学缩写，不是真实ID：

```text
P  = 高血压合并糖尿病患者
R  = ACEI或ARB方案
D1 = ACEI；D2 = ARB

E1: R --preferredRegimenFor--> P
E2: R --hasAlternativeComponent--> D1
E3: R --hasAlternativeComponent--> D2

adjacency[P]  = [E1]
adjacency[R]  = [E1, E2, E3]
adjacency[D1] = [E2]
adjacency[D2] = [E3]
```

真实邻接表还包括其他相连边，不能把上面当成完整列表。调用`repo.adjacent(R)`时，程序就拿到了R相关的边列表，这就是“为什么能接着走”的实现。

## 10. 用户说的人群，怎么定位成节点ID

`resolveRegimen(population)`首先调用`repo.seeds(population)`。[GraphRepository.java第112行起](D:/JavaProject/huawei/nexent-cognitive-agent/java-mcp/spring-ai-mcp-server/src/main/java/com/example/ict/mcp/repo/GraphRepository.java:112)的`find()`比较名称、ID、别名；`normalized()`去空白并转换为小写。

`seeds()`优先返回名称、ID或别名完全相同的结果；没有精确结果时，返回最多5个子串匹配结果，并排除文档及章节节点。`resolveRegimen()`再限制类型为`Population`。

所以传入完整“高血压合并糖尿病患者”，能够找到`N-高血压合并糖尿病患者`。这不是向量检索，也不会自动理解所有口语同义表达。模型负责从提问中提出参数，参数不合适时可能查不到。

## 11. 两跳怎样真正执行：两个循环、一个公共节点、一个同组条件

打开[DecisionSupport.java第18行起](D:/JavaProject/huawei/nexent-cognitive-agent/java-mcp/spring-ai-mcp-server/src/main/java/com/example/ict/mcp/tools/DecisionSupport.java:18)。这道题调用的`resolveRegimen()`是一个限定关系的组合查询，不是通用遍历工具。

先把匹配到的人群ID放入`targets`：

```java
Set<String> targets = new HashSet<>();
repo.seeds(population).stream().filter(n -> "Population".equals(n.path("type").asText()))
        .forEach(n -> targets.add(n.path("id").asText()));
```

第一跳：遍历边，只留下“首选方案指向目标人群”的边：

```java
for (JsonNode indication : repo.records("edges")) {
    if (!"preferredRegimenFor".equals(indication.path("relation").asText())
            || !targets.contains(indication.path("tailId").asText())) { continue; }
    String group = indication.path("regimen_group").asText();
    if (group.isBlank()) { continue; }
```

这里是循环的开头，后续代码见下段。`continue`表示当前这条不合条件，换下一条。对于E1，`tailId=P`且关系正确，匹配成功；E1的`headId=R`，所以找到了方案R。查询从P回到R，与原始箭头相反，后面记录`forward=false`。

第二跳：把刚得到的R作为参数，取R的邻边：

```java
for (JsonNode component : repo.adjacent(indication.path("headId").asText())) {
    if (!group.equals(component.path("regimen_group").asText())
            || !Set.of("hasComponent", "hasAlternativeComponent").contains(component.path("relation").asText())
            || !component.path("supporting_evidence").isArray()
            || component.path("supporting_evidence").isEmpty()) { continue; }
```

这同样是循环的开头。这里E1本身也在邻接表里，但关系不属于成分关系，所以跳过。E2、E3的关系正确、组号与E1一致、定义证据非空，就保留下来。

第二跳可连接，是因为**第一条边的`headId`与成分边关联的方案节点ID相同**。同组检查进一步防止把同名方案在另一个原文场景下的成分关系混进来。

注意当前实现依赖建图器把成分边统一写成“方案→药物”的方向；这里没有另写一条`component.headId == regimen`检查。不能把代码注释里的“核对原方向”夸大成独立完成的所有方向验证。成分定义检查也主要检查证据存在，不能替代专家复核。

第36行起将两个边对象组成路径，关键原代码是：

```java
paths.add(Map.of("nodes", List.of(name(indication.path("tailId").asText()),
                name(indication.path("headId").asText()), name(component.path("tailId").asText())),
        "hops", 2, "steps", List.of(Map.of("forward", false, "edge", indication),
                Map.of("forward", true, "edge", component)),
        "option_group", component.path("option_group").asText()));
```

于是得到两条路径：`P → R → D1`和`P → R → D2`。每条`steps`里保留完整边，所以每一步的原文、页码、条件也跟着返回，不是只返回最终药物名字。

该工具还返回方案`components`和`selection`，提醒模型每个成分组选一项。两个末端是两种可选类别，不能解释为一起服用。

这并不是让Java“理解”了首选的全部医学含义。Java按照我们指定的关系名和约束连接记录，负责确定性筛选；这条组合是否具有正确医学语义，取决于抽取规则、原文、范围和审核。

## 12. 另一个traverse_relations，才是通用有界遍历

不要混淆两个工具。`resolve_regimen`按指定模式组合，带同组和定义证据检查；`traverse_relations`按图结构找可连通路径，不能代替前者的临床范围检查。

打开[KgToolsService.java第158行起](D:/JavaProject/huawei/nexent-cognitive-agent/java-mcp/spring-ai-mcp-server/src/main/java/com/example/ict/mcp/tools/KgToolsService.java:158)。它使用队列做广度优先搜索：先看一步可到哪里，再看两步、三步。

第168行创建队列并加入起点；第175行取出队首。第178行遍历当前节点邻边，核心为：

```java
boolean forward = edge.path("headId").asText().equals(current);
String next = edge.path(forward ? "tailId" : "headId").asText();
if (walk.ids().contains(next)) { continue; }
```

如果当前节点是边的头，下一节点就是尾；否则从尾反查头。`? :`是Java条件表达式，意思是“条件成立取前者，否则取后者”。已经出现在本条路径中的节点不再走，避免A→B→A循环。

记录路径后，未到最大跳数就把新路径加入队尾：

```java
queue.addLast(new Walk(ids, steps));
```

它还限制最多3跳、最多2000次队列展开，以及最多50条返回路径；跳过`evidencedBy/containsSection/references`结构关系，避免仅因同属某文档就假装业务推理连通。具体见第166、174、180、198行及第27行结构关系集合。

因此，当前通用遍历也不是任意长度、任意关系、自动判断正确结论的推理引擎。

### 两个能帮助你检验理解的问题

第一，如果删除某条关系，模型能凭工具继续走到原终点吗？该条路径会断；但图里可能还有别的路径，而且本例还有直接`preferredFor`边。因此“这条两跳路径存在”不等于“所有查询必须依赖这两跳才能答出”。本例展示受约束的证据组合，不是强制必须多跳的效果证明。若要做实验，使用图谱副本，保留正式数据。
